## 0. Scope

Three mobile-first concerns around artifacts that have no single design home:

1. **Collapsed artifact cards** — feed and task-page artifact cards that render full content inline today need a type badge + title + ~2-line text preview. Defines the truncation rule for markdown content and the expand affordance.
2. **Mobile artifact detail view** — the tap-through target after touching a collapsed card. Decides between the existing bottom-sheet (`ArtifactViewer`) and a dedicated route, with deep-linkability, share action placement, and back navigation.
3. **Deliverable/artifact dedupe** — task pages currently render the worker completion summary under DELIVERABLES and again as a `summary`-type artifact card with identical content. Defines the suppression rule and how to attach the share affordance to the canonical block.

Section 4 covers the component inventory as observed on 2026-08-10. Section 5 covers rollout and acceptance criteria.

## 1. Collapsed artifact cards

### 1.1 Problem

`ArtifactList.tsx` (used on `/app/artifacts` and workspace artifact pages) wraps content in `<MarkdownContent>` with `line-clamp-4`, but headings, bullets, and code fences burn through the line budget without conveying information. A 500-character REPORT artifact that leads with `## Executive Summary\n\n###Background\n\n` wastes three of four preview lines on chrome.

The task-detail ARTIFACTS section (`tasks/[id]/page.tsx` lines 924–930) renders `<MarkdownContent>` inside a `max-h-48` container with a gradient fade — also not stripped — and allows up to 500 chars of raw markdown in the overflow.

### 1.2 Collapsed card layout

Every artifact card on mobile (< 640 px) must render in collapsed mode by default:

```
┌──────────────────────────────────────────────────────┐
│  [REPORT]  Weekly drift analysis          2026-08-10  │
│  Spec drift was detected across three surfaces: the  │
│  mobile feed, artifact cards, and the mission header… │
│                                              [Expand] │
└──────────────────────────────────────────────────────┘
```

Layout rules (using mobile-feed-spec design tokens):

| Element | Spec |
|---------|------|
| Type badge | IBM Plex Mono 10/600 UPPERCASE, +0.6 tracking. Background/text per existing `TYPE_STYLES` in `ArtifactList.tsx` |
| Title | IBM Plex Mono 13/600, `ink`, single line with ellipsis at card width minus badge |
| Date | IBM Plex Mono 11/400, `ink-faint`, right-aligned in the title row |
| Content preview | IBM Plex Mono 12/400, `ink-soft`, exactly **2 lines** (`line-clamp-2`). Uses the **stripped preview** (§1.3). Absent when preview is empty (link-only or file artifact) |
| Expand affordance | IBM Plex Mono 11/600, `accent-deep` UPPERCASE — `"EXPAND"` label, right-aligned in the card footer; tapping opens the detail view (§2). On desktop (≥640 px) the card is always expanded — expand affordance is mobile-only |
| Card border | 1.5px `ink`, hard shadow (4,4) `ink` |
| Intra-card spacing | Title row padding 14pt vertical, 16pt horizontal; 8pt gap between title row and preview; 12pt gap between preview and footer |

Cards with `type = 'link'` replace the content preview with the URL (truncated to card width, `ink-faint`). Cards with `type = 'file'` replace it with filename + size (`ink-faint`). Cards with `type = 'data'` use the JSON snippet.

### 1.3 Markdown truncation rule for preview

The preview string passed into the collapsed card is **not** the raw content. It must be generated by a new helper `getArtifactCollapsedPreview(content: string): string` in `apps/web/src/components/artifact-helpers.ts`.

Algorithm (order matters):

1. Strip leading/trailing whitespace.
2. Remove ATX headings: replace `/^#{1,6}\s+/gm` with `""` (drop the `#` marks; keep the heading text).
3. Remove setext heading underlines: drop lines that are entirely `=` or `-` characters.
4. Strip bold/italic markers: `/[*_]{1,3}([^*_]+)[*_]{1,3}/g` → `$1`.
5. Strip code fence delimiters: drop lines matching `/^```/` or `/^~~~`.
6. Strip inline code backticks: `/`([^`]+)`/g` → `$1`.
7. Strip list markers: replace `/^[-*+]\s+/gm` and `/^\d+\.\s+/gm` with `""`.
8. Collapse multiple blank lines into one: `/\n{3,}/g` → `"\n\n"`.
9. Collapse the result to a single space-separated string of words: split on whitespace, join with `" "`.
10. Truncate to **160 characters** at a word boundary (don't cut mid-word), append `"…"` if truncated.

**Result**: a plain-text string that fits 2 lines at IBM Plex Mono 12/400 on a 393pt card (with 32pt of horizontal padding). The 160-character budget is set for this font/width combination; at narrower widths the `line-clamp-2` CSS handles visual overflow.

**Safety property**: `getArtifactCollapsedPreview` must never throw. If content is null/empty it returns `null`; if any regex step throws it falls back to `content.slice(0, 160)`.

The existing `getArtifactPreview` function (used by `ArtifactList` today) continues to serve desktop card previews unchanged. Do not modify it.

### 1.4 Expand affordance behavior

Tapping **anywhere on the card** (not just the EXPAND label) opens the artifact detail view (§2). The EXPAND label is a visual cue, not an isolated button. It does not have a separate tap target — the entire card is the target.

On expanded state (desktop, or after manual expansion on mobile — see §2.3):
- The card renders the full content via `<ArtifactBody>` (from `ArtifactViewer.tsx`), the same renderer used in the detail view.
- The EXPAND affordance is replaced by a `"COLLAPSE"` label that snaps the card back to the 2-line preview.
- Expanded state is local component state; it resets on page re-entry.

**Non-goal for this spec**: inline card expansion is deferred. Tapping a collapsed card always opens the detail view (§2). An "expand inline" affordance may be added later as a progressive enhancement when the card is already on a full-width page (e.g. `/app/artifacts`). Do not implement inline expansion in this spec.

## 2. Mobile artifact detail view

### 2.1 Decision: bottom sheet, not a dedicated route

`ArtifactViewer.tsx` already implements a full-height bottom sheet on mobile (`animate-slide-up`, `inset-x-0 bottom-0 top-0`). The crux decision is: **keep the bottom sheet and add a URL param for deep-linking**, vs. **create a dedicated route** (`/app/artifacts/[id]`).

A dedicated route at `/app/artifacts/[id]` already exists (`apps/web/src/app/app/(protected)/artifacts/[id]/page.tsx`). It is the share target and the "Open ↗" link in `ArtifactViewer.tsx`. This creates a clean separation:

| Surface | Route | Purpose |
|---------|-------|---------|
| Task page ARTIFACTS section | inline bottom sheet | Fast in-context preview without leaving task |
| Mission artifacts list | inline bottom sheet | Fast in-context preview without leaving mission |
| Global artifacts page | inline bottom sheet | Preview without leaving the list |
| Shared artifact (external/unauthenticated) | `/share/[token]` | Public share target |
| Full artifact detail (deep link) | `/app/artifacts/[id]` | Authenticated deep link, bookmarkable |

**Ruling**: retain the bottom sheet for in-context artifact preview. Do NOT introduce a new route. The existing `/app/artifacts/[id]` page is the deep-link target, accessed via the "Open ↗" button in the sheet footer.

### 2.2 URL param for deep-linking to a specific artifact

To enable direct linking to an artifact from a notification or external reference, without relying on the bottom sheet (which requires the parent page to be loaded first):

- `/app/artifacts/[id]` renders the artifact full-page (already exists).
- `/app/tasks/[id]?artifact=<artifactId>` — the task detail page reads `searchParams.artifact`. If present and the artifact belongs to this task, the `ArtifactViewer` opens automatically at that artifact on mount. This allows a notification ("Your REPORT artifact is ready") to link directly to the viewer.

**Implementation constraint**: `searchParams.artifact` is a read-only additive param. The page server component already reads `searchParams` for other purposes; add `artifact` to the destructure and pass it as `initialOpenArtifactId` to the client component that manages `ArtifactViewer` state.

The `/app/missions/[id]` page receives the same treatment: `?artifact=<artifactId>` opens the mission `MissionArtifacts` viewer at that artifact.

### 2.3 Bottom sheet layout on mobile (393pt)

The existing `ArtifactViewer` layout is mostly correct. These are the mobile-specific constraints:

**Header** (within the sheet):
```
[X close]  Weekly drift analysis        [REPORT]
           Task: weekly-spec-status-drift
```
- Close button: 44×44pt tap target, top-left.
- Title: IBM Plex Mono 14/600, `ink`, wraps to 2 lines max, then truncates.
- Type badge: IBM Plex Mono 10/600 UPPERCASE, right of title, shrinks below it if narrow.
- Back-navigation: the close (X) button dismisses the sheet and returns focus to the card that opened it.

**Mobile chip strip** (when ≥2 artifacts):
- Horizontal scroll, no scrollbar visible.
- Each chip: IBM Plex Mono 11/500, 1.5px `ink` border, `paper` background when inactive, `accent-tint` fill + `accent` border when active.
- Chips show `artifact.title || TYPE_LABELS[artifact.type]`, truncated at 120pt per chip.

**Body**: Full-screen scroll, `overscroll-contain`. `<ArtifactBody>` renders as-is — no changes to the body renderer.

**Footer actions** (bottom of sheet, above safe-area):
```
[Share]  [Copy link]  [Unshare]    [Open ↗]   New mission →
```
- Share/Unshare/Copy link: as currently implemented in `ArtifactViewer.tsx`.
- `[Open ↗]` button: navigates to `/app/artifacts/[id]`. This is the deep-link / bookmarkable escape hatch.
- `New mission →` link: right-aligned, `ink-faint`, 11pt. Links to `/app/missions/new?artifactId=...`. Not a button — tap navigates; dismiss the sheet first via `router.push`.
- Minimum 44pt vertical height for the footer row.
- Bottom padding: `safe-area-inset-bottom + 16pt` (CSS env var).

**Share action placement**: Share is in the footer, not inline in the content body. This matches the current `ArtifactViewer` footer structure. No change needed.

**Back navigation from `/app/artifacts/[id]`** (the dedicated route, opened via "Open ↗"):
- Shows a `"← Back"` link if `document.referrer` matches `/app/tasks/` or `/app/missions/`. If no referrer (bookmarked link, notification), shows `"← Artifacts"` → `/app/artifacts`.
- Implementation: pass `?from=task&taskId=<id>` or `?from=mission&missionId=<id>` from the "Open ↗" button click. The artifact detail page reads `searchParams.from` to render the correct breadcrumb. Same param pattern as `docs/design/mobile-decision-flow.md §4.4`.

### 2.4 Edge cases

| Case | Handling |
|------|---------|
| Artifact with no content AND no url | Body renders: `"No content to display."` (already in `ArtifactBody`) |
| URL-only artifact (`type='link'`, `metadata.url` set, no `content`) | Body renders the URL as a tappable link. Preview chip shows the domain only |
| File artifact (`storageKey` set) | Body renders filename + size + download button. Preview chip shows filename. Collapsed card shows filename + size |
| Image artifact (`storageKey` + `mimeType.startsWith('image/')`) | Body renders the image full-width, max-height uncapped (scroll). Collapsed card shows `"[IMAGE]"` in place of text preview |
| Artifact with very long title (>80 chars) | Title truncates with ellipsis in both the collapsed card and the sheet header; full title in `aria-label` |
| Zero artifacts | No ARTIFACTS section header rendered; no empty-state message (existing behavior, keep) |

## 3. Deliverable/artifact dedupe

### 3.1 Problem

The task detail page renders two separate sections that can contain identical content:

**DELIVERABLES** (lines 797–881 of `tasks/[id]/page.tsx`):
- When `result.summary` exists and there are no code deliverables (`!hasCodeDeliverables`), it renders `result.summary` as `<MarkdownContent>` in a `p-5 bg-surface-2` block with an `AiFeedback` control but **no share affordance**.
- When code deliverables exist, `result.summary` renders as a subdued paragraph below the PR/commit bar.

**ARTIFACTS** (lines 883–945):
- Renders all `deliverableArtifacts` (all non-`impl_plan` artifacts).
- If the agent created a `type=summary` artifact (e.g. via `buildd` `create_artifact` with `type: 'summary'`), its content is rendered again — same markdown, same text — with a share affordance.

**Observed example** (2026-08-10, weekly-spec-status-drift task): the REPORT artifact rendered the full drift report inline in the Activity feed, and the SUMMARY artifact duplicated the deliverable block verbatim.

### 3.2 Dedupe rule

A `summary`-type artifact card is **suppressed** from the ARTIFACTS section on the task detail page when **both** conditions hold:

1. `artifact.type === 'summary'`
2. `result.summary` exists AND `artifact.content` matches `result.summary` by the **normalized-content equality** check (§3.3)

When suppressed, the artifact's share affordance is **transplanted** to the DELIVERABLES summary block, replacing the current `AiFeedback`-only footer.

**No other artifact type is ever suppressed.** The rule is narrow by design. A `content`-type artifact with the same text as `result.summary` is not suppressed — type discrimination is intentional.

### 3.3 Normalized-content equality check

Raw string equality is fragile (trailing newline, extra whitespace). Use:

```ts
function normalizeForDedupeCompare(s: string): string {
  return s.trim().replace(/\r\n/g, '\n').replace(/\n{3,}/g, '\n\n');
}

function isSummaryDuplicate(artifactContent: string, resultSummary: string): boolean {
  const a = normalizeForDedupeCompare(artifactContent);
  const b = normalizeForDedupeCompare(resultSummary);
  // Suppress if the artifact content IS the summary, or is a substring of the summary,
  // or the summary is a substring of the artifact content (agents sometimes append boilerplate).
  return a === b || b.includes(a) || a.includes(b);
}
```

The substring check (not just equality) handles the common case where the agent summary has trailing metadata that the artifact content does not, or vice versa.

**Safety**: if `artifact.content` is null, the check returns `false` — do not suppress artifacts with no content.

### 3.4 Share affordance transplant

When the summary artifact is suppressed, the DELIVERABLES block gains the artifact's share affordance:

**Before (current state):**
```
┌── DELIVERABLES ─────────────────────────────────────────┐
│  [summary markdown content]                             │
│  ─────────────────────────────────────────────────────  │
│                                          [AI feedback]  │
└─────────────────────────────────────────────────────────┘

┌── ARTIFACTS (1) ────────────────────────────────────────┐
│  [SUMMARY] Weekly summary                   [Share] [↗] │
│  [same markdown content]                                │
│                                          [AI feedback]  │
└─────────────────────────────────────────────────────────┘
```

**After (with dedupe):**
```
┌── DELIVERABLES ─────────────────────────────────────────┐
│  [summary markdown content]                             │
│  ─────────────────────────────────────────────────────  │
│  [AI feedback]               [Share] [Copy link] [Open ↗]│
└─────────────────────────────────────────────────────────┘

(ARTIFACTS section absent — no non-suppressed artifacts)
```

The transplanted footer renders:
- `AiFeedback` control (already present) — left-aligned.
- `ArtifactShareControl` component (extracted from ArtifactViewer footer logic) — right-aligned, initialized from the suppressed artifact's `shareToken` and `visibility`.
- `"Open ↗"` link → `/app/artifacts/[suppressed-artifact.id]` — rightmost, 11pt `ink-faint`.

### 3.5 Non-goals

- **Activity feed dedupe**: the Activity feed (mission live worker panel, `LiveWorkerActivity.tsx`) renders worker events, not artifact cards. Deduplication there is out of scope — artifacts are not surfaced inline in the activity feed today.
- **Multi-artifact dedupe**: only suppress when exactly one `summary`-type artifact matches `result.summary`. If the task has two `summary` artifacts with different content, suppress neither.
- **Mission-level artifact dedup**: the `MissionArtifacts` component (mission detail page) shows mission-scoped artifacts (not task-level). Task result summaries do not appear on the mission page, so there is no duplication surface there. No change needed to `MissionArtifacts`.

## 5. Open questions

**Q1: Should `getArtifactCollapsedPreview` be a server-side or client-side function?**
Lean: **shared** (importable on both sides). The helper has no I/O. Export it from `artifact-helpers.ts` which is already used in both server components and client components.

**Q2: Does the EXPAND affordance live in `ArtifactList` or in a new `ArtifactCard` component?**
Lean: **new `ArtifactCard` component** at `apps/web/src/components/ArtifactCard.tsx`. `ArtifactList` currently inlines the card JSX (lines 192–340). Extracting `ArtifactCard` is load-bearing for reuse across the task detail page (which currently has its own bespoke card JSX). A joint `ArtifactCard` primitive is the right abstraction — both surfaces become call sites of the same component, with shared collapsed/expanded state logic.

**Q3: When `?artifact=<artifactId>` is passed to the task detail page, should the sheet open server-side (pre-rendered) or client-side (via useEffect)?**
Lean: **client-side** (useEffect on mount reads the param and triggers `setOpen(true)`). Server-side pre-rendering of a modal state requires RSC/client boundary gymnastics for no observable benefit — the sheet animates in on first render either way.

## 6. Non-goals

- **iOS native artifact viewer** — this spec targets the web dashboard (responsive). The iOS native app would adapt these patterns; the native view is a separate implementation concern.
- **Inline streaming of artifact content** — artifact content is a static snapshot; streaming preview is not in scope.
- **Artifact type filtering in the collapsed card view** — filter pills are already specified in `mobile-filter-pattern.md` and apply to the list container, not individual cards.
- **Artifact versioning** — multiple versions of the same artifact key are not surfaced in the card UI; this is a future concern.
- **Dedupe of non-summary artifact types** — only `type=summary` is covered. The `content` and `report` types may produce lookalike content in the task ARTIFACTS section, but the risk is lower and the dedupe rule would need human judgment to define. Deferred.
